# Архитектура

Документ описывает, из чего состоит платформа и почему именно так. Модель данных — в [domain-model.md](domain-model.md), логика заказа — в [order-lifecycle.md](order-lifecycle.md), функционал по ролям — в [functional-spec.md](functional-spec.md), контракт — в [api.md](api.md), порядок работ — в [roadmap.md](roadmap.md).

## Что строим

Площадка заказа еды из собственной сети кафе «Кунжут». Клиент выбирает блюда, указывает адрес, система сама определяет ближайшую работающую точку, считает доставку и передаёт заказ на кухню. Везёт свой курьер. Оплата при получении или онлайн.

Это **не маркетплейс**: все точки наши, одно юрлицо, одно ядро меню. Нет кабинетов партнёров, комиссий и раздельных выплат.

## Границы системы

Входит:

- витрина меню, корзина, оформление заказа;
- определение точки по адресу, зоны и стоимость доставки;
- приём и ведение заказа операторами точек;
- назначение курьеров и статусы доставки;
- онлайн-оплата и возвраты;
- аккаунты клиентов, адреса, история заказов;
- промокоды.

Не входит и не планируется:

- кассовое ПО и товарный учёт на кухне (интеграция с iiko/r_keeper — отдельный разговор, если понадобится);
- бухгалтерия и зарплата курьеров;
- логистическая оптимизация маршрутов (один курьер — один заказ за раз);
- доставка из чужих ресторанов.

## Контуры пользователей

| Кто | Через что | Вход |
| --- | --- | --- |
| Клиент | Мобильное приложение (Expo), сайт, Telegram WebApp | Телефон + SMS-код; в Telegram — автоматически по `initData` |
| Оператор точки | Веб-панель | Логин и пароль, cookie-сессия |
| Менеджер сети | Веб-панель | Логин и пароль, доступ ко всем точкам |
| Курьер | Telegram-бот | По `telegram_id`, заведён менеджером |

Три разных механизма входа — осознанно. У клиента нет пароля (телефон и так нужен для заказа), у курьера нет веб-интерфейса, у оператора нет телефона в системе. Смешивать их в одну таблицу пользователей — значит плодить nullable-поля и проверки «а этот точно клиент?».

## Стек

| Слой | Чем | Почему |
| --- | --- | --- |
| Backend | Python 3.11, FastAPI, SQLAlchemy 2.0, Alembic | Уже написан и работает, переписывать нечего |
| База | PostgreSQL 16 | JSONB для снапшотов и полигонов, транзакции для заказов |
| Очередь | Celery + Redis | Таймеры (автоотмена неоплаченных), пуши, ретраи |
| Бот | aiogram 3 | Уже написан |
| Сайт | Vite + React + TypeScript | Общий язык и типы с мобильным приложением |
| Мобильное | Expo (React Native + TypeScript) | Один код на iOS и Android, OTA-обновления минуя ревью |
| Клиент API | `openapi-typescript` из схемы FastAPI | Типы генерируются, не пишутся руками и не расходятся |
| Прокси | Caddy | Let's Encrypt из коробки, уже настроен |

### Почему монолит, а не микросервисы

Нагрузка — десятки заказов в день, команда — один-два человека. Монолит с чистыми границами модулей (`api/routes`, `services`, `models`) разворачивается одной командой, отлаживается в одном логе и не требует распределённых транзакций там, где заказ, платёж и списание со стоп-листа должны меняться вместе. Когда одна часть начнёт мешать другой — её можно будет вынести; границы модулей это предусматривают.

### Почему React и на сайте, и в приложении

Мобильное приложение на Expo уже решено. Если сайт оставить на ванильном JS, то логика корзины, расчёт доставки, формат цен и статусы придётся писать дважды и чинить дважды. С React общими становятся типы API, модели корзины и форматирование. Разметку всё равно придётся писать отдельно — React Native не использует HTML.

Текущая витрина на ванильном JS работает и остаётся в строю, пока не дойдём до этапа 6. Выбрасывать рабочее раньше времени смысла нет.

Маршруты делятся на три группы с разными правилами доступа и разной судьбой:

- `routes/public/` — меню, заказы, аккаунт. Это контракт мобильного приложения, ломать нельзя.
- `routes/admin/` — панель. Меняется свободно, клиент и сервер катятся вместе.
- `routes/webhooks/` — ЮKassa. Без авторизации по токену, с проверкой подписи и источника.

## Совместимость API

В сторах всегда живёт старая версия приложения. Это главное ограничение, которого не было у витрины.

Правила:

1. В `/api/v1` допустимы только аддитивные изменения: новое необязательное поле, новый эндпоинт, новое значение enum, которое старый клиент может проигнорировать.
2. Ломающее изменение — это `/api/v2`, а `v1` живёт ещё минимум два релизных цикла.
3. `GET /api/v1/config` отдаёт `min_supported_app_version`. Приложение ниже — показывает экран «обновитесь» и дальше не пускает. Это аварийный выход, когда поддерживать старый контракт больше нельзя.
4. Все денежные значения — строки с двумя знаками (`"350.00"`), не float. Копейки на float ломаются.
5. Все даты — ISO 8601 с таймзоной (UTC).

## Развёртывание

Один сервер, Docker Compose. Сервисы: `postgres`, `redis`, `api`, `worker`, `telegram-bot`, `caddy`.

- Миграции применяет контейнер `api` при старте.
- Статика сайта (после этапа 6) собирается в образ и отдаётся Caddy напрямую.
- Бэкап базы — `pg_dump` по расписанию в отдельный том. **Пока не настроен, нужен до первого реального заказа.**
- Секреты в `.env`, файл не в git. `DASHBOARD_SECRET_KEY`, ключи ЮKassa и SMS — обязательно сменить перед продакшеном.

Горизонтального масштабирования нет и не планируется. Если понадобится второй инстанс `api`, нужно будет проверить: таймеры уже в Celery (переживут), сессии в cookie (переживут), кэш меню в Redis (переживёт). Блокирующее место одно — `telegram-bot` на long polling, его нельзя запускать в двух экземплярах.

## Внешние зависимости

| Сервис | Для чего | Что нужно | Если недоступен |
| --- | --- | --- | --- |
| ЮKassa | Онлайн-оплата, чеки 54-ФЗ | Договор, `shop_id`, секретный ключ, касса | Онлайн-оплата скрывается, остаётся оплата при получении |
| Яндекс.Геокодер | Адрес → координаты | API-ключ, лимит запросов | Адрес принимается как текст, зона определяется оператором вручную |
| SMS.ru (или SMSC) | Коды входа | Договор, ключ, подпись отправителя | Вход только через Telegram |
| Expo Push | Уведомления в приложении | Ничего (через Expo) | Статусы только в Telegram и по SMS |
| Telegram Bot API | Бот оператора и курьера | Токен бота | Курьеры без бота работать не смогут — это критичная зависимость |

Каждая интеграция живёт в `app/integrations/<name>.py` за своим интерфейсом, с заглушкой для разработки. Без ключей проект должен подниматься и работать на заглушках — иначе локальная разработка превращается в пытку.

## Принятые решения

**Меню переезжает в базу.** Сейчас это Python-файл. С несколькими точками, стоп-листами и ценами по точкам это неизбежно, а редактировать меню через деплой нельзя.

**Модификаторы закладываем сразу.** Соусы, острота, размер, добавки. Если добавить их позже, переделывать придётся корзину, расчёт цены, снапшот позиции в заказе и оба клиента. Сделать сразу дешевле, даже если на старте у половины блюд модификаторов нет.

**Позиции заказа — таблица, не JSON.** Сейчас `items_json`. Для вопроса «сколько донеров продали в июне» JSON неудобен, а вопрос этот зададут. При этом название и цена в позиции хранятся снапшотом: меню меняется, старый заказ должен остаться таким, каким его сделали.

**Зоны доставки без PostGIS.** Полигоны в JSONB, проверка «точка в полигоне» в Python через `shapely`. Зон на город — единицы, индекс не нужен. Если точек станут десятки и зон сотни, переход на PostGIS возможен без смены формата хранения — GeoJSON читается и тем, и другим.

**Номер заказа — последовательный, не хеш.** Сейчас `KUN-2710-B83ABEEA`: такой номер нельзя продиктовать по телефону. Нужен `КУН-2710-047` — порядковый в пределах точки и дня.

**История статусов — таблица.** Сейчас пишется в `source_json`. Это работает, но по ней нельзя построить отчёт «среднее время готовки» без разбора JSON в приложении.

**Один бот на оператора и курьера.** Роль определяется по `telegram_id` в базе. Два бота — это два токена, два процесса и два места, где ломается конфигурация, ради разделения, которое всё равно делается кодом.

## Что остаётся нерешённым

Эти вопросы не блокируют первые этапы, но ответить на них придётся:

- **Интеграция с кухней.** Пока кухня видит заказы в веб-панели. Если появится iiko, понадобится выгрузка меню и приём заказов через их API.
- **SLA и отмены.** Что делать, если точка не подтвердила заказ за 10 минут. Автоотмена, эскалация менеджеру или звонок — решать на этапе 4, когда будут реальные заказы.
- **Самовывоз.** В модели предусмотрен (`fulfillment: pickup`), в интерфейсе пока не планируется. Включить легко, но нужно понять, нужен ли он.
- **Бэкапы и мониторинг.** Нужны до первого реального заказа, не после.
