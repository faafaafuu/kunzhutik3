# Логика заказа

Жизненный цикл заказа, права на переходы, оплата, расчёт доставки и уведомления. Сущности — в [domain-model.md](domain-model.md).

## Статусы

| Статус | Что значит |
| --- | --- |
| `pending_payment` | Создан, ждём онлайн-оплату. Точка его ещё не видит |
| `new` | Оплачен или оплата при получении. Ждёт подтверждения точкой |
| `confirmed` | Точка приняла, зафиксировано обещанное время |
| `preparing` | Готовится |
| `ready` | Готов. Самовывоз — можно забирать, доставка — ждёт курьера |
| `delivering` | Курьер забрал и везёт |
| `completed` | Доставлен или выдан |
| `cancelled` | Отменён клиентом, оператором или системой |
| `rejected` | Точка отказала: нет продуктов, закрывается, адрес вне зоны |

`cancelled` и `rejected` разделены намеренно: первое — выбор клиента или сбой оплаты, второе — отказ заведения. Для отчётов это разные вещи, и смешивать их означает потерять ответ на вопрос «как часто мы сами не справляемся».

### Переходы

```text
                 оплата прошла
pending_payment ───────────────► new ──► confirmed ──► preparing ──► ready
       │                          │          │             │           │
       │ таймаут 15 мин           │          │             │           │ delivery
       ▼                          ▼          ▼             ▼           ▼
   cancelled                  rejected   cancelled     cancelled   delivering
                                                                       │
                              pickup: ready ──────────────────────► completed
                                                                       ▲
                                                                       │
                                                                  completed
```

Разрешено только то, что на схеме. Любой другой переход — ошибка 409, а не молчаливое применение.

Правила:

- из `completed`, `cancelled`, `rejected` переходов нет: это финальные состояния;
- `delivering` возможен только при `fulfillment = delivery`;
- при `fulfillment = pickup` из `ready` идём сразу в `completed`;
- `confirmed` обязателен: нельзя из `new` прыгнуть в `preparing`, потому что именно в `confirmed` фиксируется обещанное клиенту время;
- назначение курьера — **не статус**, а заполнение `courier_id`. Курьера можно назначить на `confirmed`, `preparing` или `ready`.

### Кто что может

| Переход | Клиент | Оператор | Курьер | Система |
| --- | --- | --- | --- | --- |
| `pending_payment → new` | — | — | — | да (вебхук оплаты) |
| `pending_payment → cancelled` | да | да | — | да (таймаут) |
| `new → confirmed` | — | да | — | — |
| `new → rejected` | — | да | — | — |
| `new/confirmed → cancelled` | да | да | — | — |
| `confirmed → preparing` | — | да | — | — |
| `preparing → ready` | — | да | — | — |
| `preparing/ready → cancelled` | — | да | — | — |
| `ready → delivering` | — | да | да (взял заказ) | — |
| `delivering → completed` | — | да | да (доставил) | — |
| `ready → completed` (самовывоз) | — | да | — | — |

Клиент отменяет сам только до `preparing`: после этого еда уже готовится, и отмена — разговор с оператором. В приложении после `preparing` кнопка отмены меняется на «Позвонить в кафе».

Оператор может всё по своей точке, включая отмену на любом нефинальном статусе. Это сознательно: в реальной работе бывает всё, и запрет приведёт к заказам-зомби.

Каждый переход пишет строку в `order_status_events` с `actor_type` и `actor_id`. Без исключений — иначе история врёт.

## Оформление заказа

```text
1. Клиент собрал корзину (на клиенте, сервер корзину не хранит)
2. POST /api/v1/orders/quote  — проверка и расчёт, ничего не создаёт
3. POST /api/v1/orders        — создание
```

### Расчёт (`quote`)

Шаг за шагом, в этом порядке:

1. **Адрес → координаты.** Если клиент выбрал сохранённый адрес, координаты уже есть. Иначе геокодер. Не удалось — ошибка «уточните адрес».
2. **Подбор точки.** Берём активные точки, у которых `accepts_delivery`, адрес попадает в активную зону и которые сейчас открыты. Если подходит несколько — та, чья зона с меньшим `priority`, при равенстве — ближайшая по координатам.
3. **Нет подходящей точки** — отвечаем, почему именно: вне зоны доставки или все точки закрыты. Это разные сообщения, и клиенту важно понимать разницу.
4. **Проверка позиций.** Каждое блюдо есть в `venue_menu_items` выбранной точки, `is_available = true`, `unavailable_until` в прошлом или пуст. Модификаторы принадлежат группам этого блюда, количество выбранных укладывается в `min_choices`/`max_choices`.
5. **Цены.** Только с сервера: `price_override` или `base_price`, плюс `price_delta` модификаторов. Цена, присланная клиентом, игнорируется полностью.
6. **Суммы.** `items_total` → промокод → `discount_total` → `delivery_fee` (0, если `items_total >= free_delivery_from`) → `total_amount`.
7. **Минимальная сумма.** `items_total < min_order_amount` зоны — отказ с указанием, сколько не хватает.
8. **Время.** `promised_at = now + prep_time_minutes + eta_minutes`. Для заказа ко времени — `scheduled_for`, и точка должна быть открыта на тот момент.

`quote` возвращает тот же расчёт, что и создание заказа, и вызывается при каждом изменении корзины или адреса. Клиент никогда не считает итог сам — иначе суммы разойдутся.

### Создание

Всё в одной транзакции:

1. Повторить расчёт заново. Между `quote` и созданием могло поменяться что угодно: стоп-лист, цена, время работы. Если итог отличается от присланного клиентом `expected_total` — ответ 409 с новым расчётом, клиент показывает «цена изменилась».
2. Выдать `daily_seq`: `SELECT ... FOR UPDATE` по `(venue_id, order_date)`, инкремент. Собрать `number`.
3. Создать `orders`, `order_items`, `order_item_modifiers`.
4. Промокод — `SELECT ... FOR UPDATE`, проверить лимиты, увеличить `used_count`.
5. Записать событие `→ new` или `→ pending_payment`.

Если оплата онлайн — заказ создаётся в `pending_payment`, и только после этого, **вне транзакции**, создаётся платёж в ЮKassa. Внешний вызов внутри транзакции держит блокировки на время сетевого запроса; при таймауте ЮKassa это заблокирует выдачу номеров всей точке.

Если создание платежа не удалось — заказ отменяется с `cancel_reason = payment_init_failed`, клиент видит «не удалось начать оплату».

## Оплата

### Онлайн

```text
заказ (pending_payment)
   └─► создаём платёж в ЮKassa с Idempotence-Key
         └─► клиенту уходит confirmation_url
               └─► клиент платит
                     └─► ЮKassa шлёт вебхук payment.succeeded
                           └─► payment.status = succeeded
                               order.payment_status = paid
                               order → new, точка получает заказ
```

Обязательные условия:

- **Идемпотентность вебхука.** ЮKassa доставляет повторно при любой ошибке. Обработчик ищет платёж по `provider_payment_id` и, если статус уже конечный, отвечает 200 и ничего не делает.
- **Проверка источника.** Вебхук принимается только с IP-диапазонов ЮKassa. Тело не содержит подписи, поэтому сумма и статус **перепроверяются запросом к API ЮKassa** по `payment_id` — на тело вебхука полагаться нельзя.
- **Чек 54-ФЗ.** В запрос создания платежа передаётся `receipt` с позициями, ставками НДС и контактом клиента. Без этого онлайн-оплату нельзя включать на продакшене.
- **Таймаут.** Задача в Celery через 15 минут: если заказ всё ещё `pending_payment` — отменить, `cancel_reason = payment_timeout`.

Статус `waiting_for_capture` не используем: платежи создаются с `capture: true`, двухстадийность для доставки еды не нужна.

### При получении

`payment_method` = `cash` или `card_on_delivery`, `payment_status` = `not_required`. Заказ сразу в `new`. Факт получения денег система не отслеживает — это касса точки.

### Возврат

Отмена заказа с `payment_status = paid` создаёт возврат в ЮKassa на полную сумму. Частичный возврат (убрали позицию) — только вручную оператором через панель, отдельным действием. Возврат не мгновенный: `refunds.status` обновляется вебхуком, до этого заказ показывает «возврат в обработке».

## Доставка и курьеры

### Назначение

Два пути:

1. **Курьер берёт сам.** На смене он видит в боте свободные заказы своей точки (`courier_id IS NULL`, статус `confirmed`/`preparing`/`ready`) и нажимает «Взять». Первый успевший получает заказ — на уровне базы это `UPDATE ... WHERE courier_id IS NULL`, проигравший видит «заказ уже взяли».
2. **Оператор назначает.** Из панели, на любого курьера на смене.

Переназначение возможно до `delivering`. После — только через снятие статуса оператором.

### Действия курьера в боте

| Кнопка | Что делает | Когда доступна |
| --- | --- | --- |
| «Взять» | `courier_id = я` | Заказ свободен, я на смене |
| «Забрал» | `ready → delivering` | Заказ мой и в `ready` |
| «Доставил» | `delivering → completed` | Заказ мой и в `delivering` |
| «Проблема» | Уведомление оператору, статус не меняется | Заказ мой, не финальный |

Курьер не может отменить заказ. «Проблема» зовёт оператора — решение за человеком.

### Смены

Курьер открывает смену в боте (`/shift`), закрывает по окончании. Вне смены он не получает уведомлений о новых заказах и не видит свободные. Незакрытая смена закрывается автоматически в полночь по таймзоне точки.

## Уведомления

| Событие | Клиент | Точка | Курьер |
| --- | --- | --- | --- |
| Заказ создан (`new`) | подтверждение с номером | пуш в бот + звук в панели | — |
| `confirmed` | «приняли, будет к 19:40» | — | — |
| `ready`, доставка | — | — | всем на смене: новый свободный заказ |
| Курьер взял | — | в панели | — |
| `delivering` | «курьер выехал» | — | — |
| `completed` | «приятного аппетита» + просьба оценить | — | — |
| `cancelled` / `rejected` | причина | — | если был назначен |
| Оплата не прошла | «не удалось оплатить» | — | — |

Каналы по приоритету: пуш в приложение (если есть активное устройство) → сообщение в Telegram (если клиент пришёл оттуда) → SMS (только критичное: отмена и подтверждение, потому что платно).

Отправка уведомлений — всегда через Celery, никогда синхронно в обработчике запроса. Телеграм или пуш-сервис могут отвечать секундами, и клиент не должен это ждать.

## Вход клиента

### По телефону

```text
POST /api/v1/auth/otp/request  { phone }
   → код из 4 цифр, SMS, живёт 5 минут
POST /api/v1/auth/otp/verify   { phone, code }
   → access (15 мин) + refresh (60 дней)
```

Ограничения, без которых это дыра:

- не больше 1 запроса кода на телефон в 60 секунд;
- не больше 5 запросов на телефон в час и 20 на IP в час;
- не больше 5 попыток ввода на код, потом код сгорает;
- в базе хранится хеш кода;
- ответ на `request` одинаков и для существующего клиента, и для нового — иначе по нему можно проверять, зарегистрирован ли номер.

Клиент создаётся при первом успешном `verify`.

### Из Telegram

WebApp передаёт `initData`. Сервер проверяет подпись по токену бота и `auth_date` не старше 24 часов. При успехе ищет клиента по `telegram_id`, при отсутствии — создаёт. SMS не нужен.

Если у клиента с таким `telegram_id` ещё нет телефона, он запрашивается при первом заказе: курьеру нужно куда-то звонить.

### Токены

Access — JWT на 15 минут. Refresh — на 60 дней, в базе не хранится, отзывается сменой `DASHBOARD_SECRET_KEY` (грубо, но на старте приемлемо). Полноценный отзыв токенов — когда появится «выйти на всех устройствах».

Гостевой заказ — без токена, только имя, телефон и адрес. Поддерживаем: заставлять регистрироваться ради первого заказа — верный способ его потерять.

## Что считаем по истории

Из `order_status_events` и отметок времени:

- время подтверждения — `confirmed_at - created_at`;
- время готовки — `ready_at - confirmed_at`;
- время доставки — `delivered_at - picked_up_at`;
- опоздания — `delivered_at > promised_at`;
- доля отказов точки — `rejected` к общему числу.

Это и есть ответ на вопрос «как работает кухня», ради которого история выносится в таблицу.
