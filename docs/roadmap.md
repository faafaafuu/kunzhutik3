# Порядок работ

Этапы упорядочены по зависимостям, а не по желанности. Каждый заканчивается чем-то, что можно показать и проверить.

Оценки — в человеко-днях при неспешной работе, для понимания соотношения, а не для календаря.

## Этап 0 — то, что уже есть ✅

Выделено из `kunzhutik-content-factory` 27.10.2026.

- Витрина меню с корзиной и оформлением, адаптив, Telegram WebApp.
- API меню и заказов, цены считаются на сервере.
- Панель оператора: список заказов, смена статуса.
- Авторизация операторов, роли `operator` и `admin`.
- Telegram-бот: меню, контакты, заказы, статусы.
- Docker Compose, Caddy, миграции при старте, 9 тестов.

Ограничения: одна точка, меню в Python-файле, позиции заказа в JSON, номер заказа нечитаемый, нет клиентов, оплаты, курьеров и зон.

- [ ] Статусы и машина переходов с проверкой прав
- [ ] Перенос каталога из `catalog.py` в базу скриптом наполнения
- [ ] Подбор точки по адресу, проверка зоны, расчёт доставки
- [ ] Геокодер за интерфейсом, с заглушкой для разработки
- [ ] `POST /orders/quote`

Готово, когда: заказ с модификаторами оформляется на точку, подобранную по адресу, с правильной стоимостью доставки и читаемым номером.

## Перед первым реальным заказом

Не этап, а список, без которого запускаться нельзя:

- [ ] Бэкап базы по расписанию, с проверенным восстановлением
- [ ] Сменены `DASHBOARD_SECRET_KEY` и пароль администратора
- [ ] `TELEGRAM_ALLOWED_USER_IDS` заполнен — иначе статусы заказов меняет любой, кто нашёл бота
- [ ] Мониторинг: жив ли api, бот, worker; оповещение при падении
- [ ] Логи с ротацией
- [ ] Политика конфиденциальности и согласие на обработку персональных данных: собираем телефон и адрес, это 152-ФЗ
- [ ] Проверен полный цикл на реальном заказе с реальной оплатой

## Порядок и почему он такой

Домен первым, потому что переделывать модель данных под уже работающим приложением дороже всего. Клиенты до оплаты, потому что платит конкретный человек с телефоном. Оплата до курьеров, потому что отмена оплаченного заказа — это возврат, и курьер в этой логике ничего не меняет. Управление после курьеров, потому что до этого момента меню и зоны меняются редко и правятся скриптом, а вот заказы идут каждый день. Фронтенды в конце, потому что им нужен готовый API — иначе они будут переписываться вслед за каждым изменением контракта.
